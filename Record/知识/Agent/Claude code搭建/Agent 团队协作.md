# Agent 团队协作

## 核心结论

多 Agent 协作需要明确负责人、共享任务状态、独立消息上下文和可追踪的控制协议。教程由 Lead 提议分工并等待用户确认，常驻队友在 WORK 与 IDLE 间切换，通过消息邮箱和共享任务板继续接单。

## 解释与适用条件

常驻队友与一次性子 Agent 不同：它保留自己的上下文，可接收后续消息和任务。每个成员使用独立消息历史；文件邮箱传递普通消息、结果和控制事件，运行框架把 Lead 收到的事件送入下一轮。任务结果与“已空闲、可接新工作”是两个不同事件。

空闲队友先处理消息，再发现就绪任务。扫描只产生候选列表；真正领取时须在锁内重新检查任务状态、依赖、负责人和工作目录，并原子写入，防止多个成员同时取得同一任务。任务可绑定独立 Git worktree，工具据任务绑定选择工作目录；worktree 隔离工作目录与分支，并不限制 Shell 可访问的其他资源。完成任务与清理 worktree 是两个步骤。

关闭请求和计划审批使用带请求 ID、类型及状态的协议，便于对应回复并防止重复处理。若任务要求先批准计划，工具分发层会在批准前拦截 Shell、写入和编辑；任务身份改变时旧批准失效。教程中的团队设计适用于可明确分工且并行收益足以抵消协调成本的任务。
